# DevPilot 四项工程评估（2026-10-05）

面向开发、QA 与运维。本轮完成 RAG 参数对照、服务负载、故障注入及安全/回归检查，**没有调用付费模型**。结果来自本机真实源码、HTTP、Worker 进程、Docker 沙箱及专用 MySQL/Redis；服务任务运行器是可控负载，不代表模型修复吞吐。RAG 使用本轮冻结源码，期间工作流有另一次独立更新，不能将冻结检索语料视为最新 HEAD 的全部字节。

机器摘要见 [JSON](engineering_evaluation_2026-10-05.json)。本轮最有价值的发现是：检索排名可以改善；并发吞吐增长不线性；沙箱超时存在容器残留且已修复；取消任务的队列收尾曾有缺口，后续已[修复并复测](cancellation_fix_2026-10-05.md)。

## 1. RAG 参数与检索质量

语料为冻结的 DevPilot 后端源码，共 81 个可索引文件，使用本地 `all-MiniLM-L6-v2` 真实 embedding（384 维）。32 条人工文件标注查询按查询拆成 development 16 条、validation 16 条；包含一条中文查询。不是旧的微型 fixture 15 条评测，也不是外部大仓库基准。标注见 `backend/benchmarks/retrieval_engineering.json`。

网格共 **720 组配置、23,040 条查询结果**：

| 参数 | 对照值 |
|---|---|
| Python 分块 | AST；固定窗口 |
| 窗口长度 | 40、80、160 行，长度对照固定 overlap=15 |
| 重叠量 | 80 行窗口下分别为 0、15、30 行 |
| 返回文件数 top_k | 1、3、5、10 |
| 每路候选数 candidate_k | 10、20、40 |
| RRF 常数 | 10、60 |
| 向量路权重 | 0、0.25、0.5、0.75、1；0/1 为纯 BM25/向量消融 |

比较使用产品的分块与融合实现，新增可选参数的默认值保持原行为。网格缓存真实查询向量与每路前 40 候选排名，只重算融合；随后查询耗时测量恢复真实编码、排序和 BM25 构建，预热后每查询重复三次，不包含索引构建。网格参数组合中部分纯单路配置排名相同，720 不是 720 个独立实验样本。

选参只按 development 的 Recall@5、MRR@5 降序，然后上下文字符数升序。最终选出 **80 行窗口、overlap=0、top_k=5、candidate_k=20、RRF=10、向量权重=0.5**。没有据 validation 排名挑最好看的配置，也没有修改产品默认配置。

| 16 条 validation 查询 | 默认 AST 配置（按 top_k=5 比较） | development 选出的配置 |
|---|---:|---:|
| 文件级 Recall@5（宏平均） | 68.75% | 84.38% |
| MRR@5 | 0.4604 | 0.6615 |
| 文件级 Precision@5 | 15.00% | 17.50% |
| 平均返回内容字符数 | 22,247 | 11,647 |
| 平均温查询耗时（32 查询×3 次） | 37.25 ms | 40.40 ms |
| 温查询 P95 | 50.43 ms | 54.43 ms |

验证查询 Recall 增加 **15.63 个百分点**，MRR 增加 0.2010，上下文字符数减少 **47.65%**；平均查询耗时增加约 8.5%。延迟使用全部 32 查询，不能和仅 validation 的质量列混作同一样本口径。字符数不是模型 Token，更不是实际账单；文件命中也不代表片段包含完整修复上下文。

选定配置的 top_k 权衡如下：

| top_k | validation Recall@K | MRR@K | 平均上下文字符数 |
|---|---:|---:|---:|
| 1 | 50.00% | 0.5000 | 2,600 |
| 3 | 78.13% | 0.6458 | 6,811 |
| 5 | 84.38% | 0.6615 | 11,647 |

增加 K 可以补召回，但上下文也增长。不同融合参数未必都优于默认：例如固定 AST/candidate=20/RRF=60 时，纯 BM25、等权融合、纯向量的 validation Recall@5 分别为 65.63%、68.75%、75.00%，MRR 分别为 0.4375、0.4604、0.4479，不能只靠一个指标选策略。

完整配置见 [参数 CSV](rag_parameters_2026-10-05.csv)，默认/选定配置逐查询结果见 [查询 CSV](rag_queries_2026-10-05.csv)。验证标注的目标文件与开发标注有重合；扩充网格前也已经查看过早期验证结果。因此这是本项目开发评估，不能称为盲测、跨仓库泛化或严格的修复能力消融。未评估生成答案忠实度，也未新增真实模型 RAG/无 RAG 修复对照。embedding 缓存的模型 revision 未固定。

## 2. 服务性能

Windows 本机、单 API 进程、独立 Worker、专用 SQLite，真实 localhost HTTP。每个并发档重复三次；请求延迟使用高精度 `perf_counter`，百分位由全部三轮响应合并计算，吞吐为请求总数/三轮墙钟总时长。是有界闭环负载，尚未测开放到达率下的饱和点。

读负载查询含 20 条各 512 字符事件的任务详情，每档共 720 次：

| 客户端并发 | 请求/秒 | P95 | API 平均 CPU（单核=100%） | API 采样峰值工作集 |
|---|---:|---:|---:|---:|
| 1 | 76.93 | 38.51 ms | 31.55% | 219.11 MiB |
| 4 | 164.12 | 49.26 ms | 101.87% | 220.35 MiB |
| 16 | 209.00 | 84.14 ms | 176.44% | 231.82 MiB |
| 32 | 221.77 | 242.23 ms | 207.91% | 246.82 MiB |

执行负载为 API 入队→真实 Worker→持久化事件→SSE，运行器进行 50ms 可控等待并产生 start/final 事件；客户端并发 16，每个 Worker 档共 144 次：

| Worker 并发 | 完成任务/秒 | 请求到 SSE 完成 P95 | 请求到运行器开始平均耗时 |
|---|---:|---:|---:|
| 1 | 6.95 | 2,281.01 ms | 1,659.09 ms |
| 2 | 8.24 | 3,539.03 ms | 1,348.43 ms |
| 4 | 11.70 | 1,557.71 ms | 834.59 ms |

**3,312 次测量请求均没有响应或内容错误。** Worker=2 的三轮 P95 为约 1,675～4,166 ms，波动保留；没有删除较慢的一轮。增加并发没有产生线性吞吐收益，也不能仅据三档数据确定瓶颈或生产最优参数。请求到运行器开始包含 HTTP、入队、排队与领取，不能称为纯队列等待；它用跨进程单调时钟，精度低于请求延迟计时器。

CPU/工作集统计包含 Windows 虚拟环境启动器与其应用子进程，不包含负载客户端及数据库容器；CPU 超过 100% 表示使用超过一个核。工作集受系统换页影响，不是 Python 堆大小或内存泄漏结论。逐轮资源与 P99 见 [性能 CSV](service_performance_2026-10-05.csv)。MySQL/Redis 在本轮完成语义与集成回归，但未做对应后端负载横向比较；未测远端网络、多 API 实例、长时间稳定性或真实 LLM 饱和吞吐。

## 3. 运行可靠性

| 场景 | 结果与口径 |
|---|---|
| 真实 Worker 进程强制终止 | kill 后约 29.97 秒自然租约到期，任务隔离为 interrupted、队列 dead；到期前其他 Worker 不能领取 |
| 确认旧进程停止后显式恢复 | 恢复成功、任务 completed；没有自动接管或副作用恰好一次承诺 |
| 执行器连续故障 | 三次尝试后 dead，start 事件三次，重试有界 |
| 跨进程 API 取消 | 约 1.02 秒后 Worker 退出，任务 cancelled，仅一个 cancelled 事件 |
| 存储异常使租约校验不可用 | 校验返回 false；这是进程内异常注入，不是真实网络分区 |
| SDK 真实本地 HTTP：429→429→200 | 共三次请求后成功，没有访问供应商 |
| SDK 真实本地 HTTP：401 | 一次失败，不重试 |
| SDK 真实本地 HTTP 超时 | 0.1 秒配置下约 0.125 秒返回 APITimeoutError，关闭重试 |

原批次七项探针通过基础断言，但**当时取消后队列状态仍为 queued**：业务 cancelled 状态会阻止再执行，队列仍可能进行多余领取并耗尽 attempts。原始 JSON 保留该发现。随后已增加不可重试收尾并通过三后端与真实进程复测，详见[取消收尾修复](cancellation_fix_2026-10-05.md)；没有改写旧实验数据。租约校验与写入间的竞争窗口、工具副作用无法抢占、同仓库任务互斥、多机故障切换仍未验收。

## 4. 安全与回归

- 真实 HTTP：缺失/错误 Key 的读取、执行、SSE、取消均为 401；合法 Key 可通过；健康探针无需 Key；白名单外目录与父目录绕过返回 422。符号链接逃逸、历史路径重校验、生产无 Key 拒绝启动等在回归套件覆盖。
- 真实 Docker：仓库只读挂载的写入被拒绝，禁网连接被拒绝，宿主文件没有创建。
- **发现并修复超时容器残留**：原实现只杀 docker CLI，2 秒超时后仍有一个执行容器。现在给每次容器唯一名称，超时定向 `docker rm -f`，并返回清理是否确认；复测无新增残留。清理失败不会伪称容器已终止。单元测试覆盖成功/失败收口。
- 后端最终 **216 passed、0 skipped、0 failures、0 errors**，包含专用真实 MySQL 8.4/Redis 7 集成、队列独占领取、fencing、背压、迁移、检查点、测试防篡改与独立裁判。此前本轮 210 项已全部通过；库内另一次工作流更新加入六项用例，最后复跑共 216 项。
- 前端 **8 passed**，类型检查与生产构建成功；评测视图仍有大于 500kB 的产物警告，未把构建成功当作性能验收。
- 初次回归的一个失败由宿主环境变量覆盖用例自带假配置引起，修复为显式测试变量后复跑通过；不是模型调用失败。Windows 编码告警通过隔离运行的 UTF-8 模式消除。

这些检查不能替代多租户权限、全面渗透测试、Docker Host 安全或生产网络验收。既有演示服务没有纳入此次隔离服务验收。

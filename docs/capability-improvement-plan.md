# DevPilot 能力边界改进计划

更新时间: 2026-10-04

## 失败原因系统性分析

基于第五轮 4 个失败实例 (pydicom-1139, astroid-1333, astroid-1978, sqlfluff-1763) 的分析,失败原因可以归类为三类:

### 类型 1: 探针覆盖不全 (1/4)
- **实例**: pydicom-1139
- **现象**: Agent 主动调用 `protocol_probe`,4 个探针全部通过,但目标测试 `test_next` 失败
- **根因**: 探针覆盖了 `__iter__`/`__contains__`/空迭代/多轮迭代,但**遗漏了旧式 `next(obj)` 协议兼容性**
- **本质**: 提示词已要求"旧式 next() 兼容",但模型在构造探针时未验证

### 类型 2: 超出运行时探针范围 (2/4)
- **实例**: astroid-1333 (模块包加载), astroid-1978 (`getattr` 捕获)
- **现象**: 涉及静态类型推断、AST 字符串化、模块加载语义等深层语义
- **根因**: `protocol_probe` 只能观察运行时行为,无法验证编译时/静态分析能力
- **本质**: 这是模型推理能力的边界,超出了"运行时协议观察"机制的覆盖范围

### 类型 3: 仓库特定知识缺失 (1/4)
- **实例**: sqlfluff-1763
- **现象**: 涉及 `safe_create_replace_file` 等仓库特有 API
- **根因**: 缺乏对特定仓库架构、约定和领域知识的理解
- **本质**: 通用工具无法提供特定仓库的上下文

## 改进方案

### 方案 A: 增强探针检查清单 (针对类型 1)

**目标**: 让模型在构造探针时更全面地覆盖协议要求

**具体改进**:
1. **显式化探针检查清单**: 在提示词中将"旧式 next() 兼容"等要求转化为可验证的探针模板
2. **探针覆盖率验证**: 在执行探针前,要求模型自我检查是否覆盖了提示词中的所有协议点
3. **失败案例反馈机制**: 当测试失败时,分析是否存在未被探针覆盖的协议点

**预期效果**: 
- 提升迭代器/协议类问题的通过率
- 不增加 Token 成本(只是重组现有提示词)
- 可能需要 1-2 轮额外的探针调用

**风险**: 
- 可能增加探针调用次数,消耗轮次预算
- 如果模型本身理解能力不足,再详细的检查清单也无济于事

### 方案 B: 引入静态分析工具 (针对类型 2)

**目标**: 为超出运行时探针范围的静态语义提供观察手段

**具体改进**:
1. **新增工具 `analyze_static_semantics`**: 
   - 集成 `mypy`/`pyright` 进行类型推断分析
   - 使用 `ast.unparse` 观察 AST 字符串化
   - 提供模块导入关系和符号解析
2. **提示词增强**: 引导模型在遇到类型/AST 问题时优先使用静态分析工具
3. **工具预算调整**: 可能需要增加轮次上限或调整轮次分配策略

**预期效果**:
- 潜在提升 astroid 等静态分析相关问题的通过率
- 提供更精确的类型推断和符号解析能力

**风险**:
- 工具实现复杂度高,需要处理不同仓库的静态分析配置
- Token 和轮次成本显著增加
- 可能引入新的环境依赖问题

### 方案 C: 增强仓库上下文理解 (针对类型 3)

**目标**: 帮助 Agent 理解仓库特定的架构和约定

**具体改进**:
1. **架构文档提取**: 
   - 自动读取 `CONTRIBUTING.md`/`ARCHITECTURE.md`/`docs/` 中的架构说明
   - 提取仓库特定的 API 约定和模式
2. **代码模式学习**:
   - 分析仓库中类似功能的实现模式
   - 提供"在本仓库中,类似功能通常如何实现"的参考
3. **改进 RAG**:
   - 当前 RAG 无收益可能是因为检索策略不当
   - 尝试基于问题类型的动态检索策略

**预期效果**:
- 提升仓库特定问题的通过率
- 可能重新发现 RAG 的价值

**风险**:
- 实现复杂,需要针对不同仓库调优
- 可能增加大量 Token 成本
- 文档质量参差不齐,自动提取可能引入噪声

## 实验验证计划

### 原则
1. **冻结基线**: 先冻结当前策略作为基线
2. **单变量对照**: 每次只测试一个改进方案
3. **未调参实例**: 从剩余的 SWE-bench Lite dev split 中选择未见过的实例
4. **重复验证**: 每个实例至少运行 3 次,计算置信区间

### 阶段 1: 方案 A - 增强探针检查清单 (优先级最高)
- **理由**: 成本最低,实现最简单,pydicom-1139 是明确的"探针遗漏"案例
- **实验设计**:
  1. 改进提示词中的探针检查清单
  2. 在 pydicom-1139 的**同类型**未见实例上验证(不是 pydicom-1139 本身!)
  3. 选择其他包含迭代器/协议问题的新实例
- **成功标准**: 
  - 在新实例上,探针覆盖率提升
  - 迭代器类问题通过率提升 > 15%
  - Token 增长 < 10%

### 阶段 2: 方案 C - 增强仓库上下文 (优先级中等)
- **理由**: RAG 当前无收益,但可能是策略问题而非方向问题
- **实验设计**:
  1. 改进 RAG 检索策略(基于问题类型动态检索)
  2. 添加架构文档自动提取
  3. 在新实例上对比 baseline vs 新 RAG
- **成功标准**:
  - 新 RAG 策略在新实例上通过率 > baseline
  - 不引入显著的 Token 或延迟增长

### 阶段 3: 方案 B - 静态分析工具 (优先级最低)
- **理由**: 实现成本高,且 astroid 问题可能真的超出模型能力边界
- **实验设计**:
  1. 实现 `analyze_static_semantics` 工具
  2. 在 astroid 相关的新实例上验证
- **成功标准**:
  - 静态分析类问题通过率提升 > 20%
  - 证明改进的价值大于实现和维护成本

## 不应该做的事情

1. ❌ **不要针对已知失败题调参**: pydicom-1139/astroid-1333/astroid-1978/sqlfluff-1763 已经是开发集,不能用它们的结果来评估改进效果
2. ❌ **不要追求 100% 通过率**: 4/11 失败可能部分是模型能力边界,不是所有问题都能通过工程手段解决
3. ❌ **不要增加模型调用轮次**: 当前 14 轮已经是权衡的结果,第六轮实验证明 24 轮没有收益
4. ❌ **不要盲目堆功能**: 每个改进都必须通过未调参实例验证,否则只是过拟合

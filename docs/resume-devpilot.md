# DevPilot 简历表述与面试依据

面向 AI 应用 / Agent 开发岗位。以下内容以代码、保存的实验结果及本机验证为依据；突出工程贡献，避免把合成回归、真实缺陷评测和生产验收混成一个成功率。

## 可直接使用的版本

**DevPilot｜面向代码仓库的智能研发平台**

技术栈：Python、FastAPI、Vue 3、Tool Calling、Hybrid RAG、MCP、Docker、Redis、MySQL

- 构建 Planner / Coder / Tester / Reviewer 协作流程与单 Agent 执行模式，打通 GitHub Issue 导入、计划审批、代码修改、隔离测试及 Draft PR 发布，结合 SSE 与持久化 Trace 实现全过程追踪和断线续传。
- 实现 AST 分块、BM25 与向量检索融合的 Hybrid Code RAG，按仓库规模、目标文件结构和问题语义动态选择检索与工具策略，结合上下文压缩、工具观测去重及 Prompt Cache 统计控制长任务成本。
- 设计 API/Worker 分离的持久化任务执行链，采用 SQL 行锁和 Redis Lua 完成原子领取，接入租约心跳、令牌校验、有限重试与背压；补齐 API Key、仓库白名单及 MySQL 共享状态，并通过三后端并发与端到端集成验证。
- 定位并修复结构化输出解析、流程收尾及测试结果采信故障，在 **9 个自建 Python 用例×3 次重复回归中取得 27/27 通过**，保存候选工作区并通过独立裁判重放复核；另以 SWE-bench 真实缺陷评测检验复杂任务边界。

版面紧张时保留第 1、3、4 点。不要将 27/27 的范围从“自建 Python 用例回归”改成“SWE-bench”或“真实仓库修复”。

## 面试追问如何回答

**为什么历史测试通过率高，端到端成功率却低？**
旧批次 multi_no_rag 的固定测试为 26/27，但 success 只有 14/27。success 同时要求独立 verifier 通过和没有执行链 error；模型输出类型、JSON 解析和角色收尾都可能让流程失败，即使候选代码已经通过测试。修复后的批次二者均为 27/27。

**100% 是什么口径？**
9 个 Python 自建基础用例，每个重复 3 次，仅 multi_no_rag；没有扩大到 TypeScript/Java、大仓库、所有策略或 SWE-bench。27 份候选工作区已重新通过独立 verifier，Agent 修改的测试不用于判分。

**能说“从 52% 提升到 100%”吗？**
可以在项目讲解中说明“历史回归批次由 14/27 到新批次 27/27”，但数据集指纹与实现有变化，属于历史比较，不能说是严格同条件消融或把提升全部归因于某一项修复。简历主版本采用更稳妥的“新批次 27/27 通过”。

**真实缺陷表现如何？**
第五轮 20 题抽样中 9 题未通过环境校准，11 题各运行 3 次，自研 verifier 为 21/33。官方 harness 对同批 33 份补丁复核为 18 resolved、12 unresolved、3 镜像错误，另有金补丁也失败的环境个案；不能作为公开榜单成绩。本次合成回归不会改写这些真实结果。

**是生产级自动故障切换吗？**
已实现生产部署所需的若干基础能力，并通过本机真实 MySQL/Redis 验证。执行层会校验 owner/token/租约，失效时停止写入；校验到写入有竞争窗口，Redis 和业务库也不是同一事务。工具副作用不能抢占，因此租约失效先隔离、确认旧进程停止后恢复。尚未验收真实多机故障切换、仓库互斥或多租户隔离。

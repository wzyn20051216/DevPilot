# DevPilot 配图提示词第二版

本版按用户参考图重新设计。首版的大字卡片和平铺框图只作草稿，不作为飞书交付图。内容依据当前源码与冻结实验，风格参考不提供任何项目事实。

## 统一视觉提示词

参考所附「AI × CAD 自动化项目图解」的版式质量，重新创作 DevPilot 技术信息图。只借鉴：白底、深海军蓝标题、电光蓝细描边、分层模块矩阵、左侧层级标签、统一小图标、紧凑排版、右侧知识解释栏、底部深蓝总结带。不要复制参考图的 CAD 模块、软件、徽标、论断、手机截图边框和浮动按钮。

采用设计精细的技术杂志信息图，而不是巨大的标题和几块浅色卡片。标题约占画面高度 8%，主内容约 78%，总结与脚注约 14%；外边距为短边 4%。竖版优先 3:4，表格、时序和对比图采用横版 4:3。高分辨率、边缘清楚，图中中文完整可读。

顶部：小型六边形 DevPilot 抽象图标、细蓝分隔线、系列眉题「DevPilot 工程实践图解」、页码「01 / 10」等。主标题两行以内，关键主张只用深蓝与一处暖橙强调。不能让标题挤占主体。

主体：用 1px 淡蓝框构建秩序，适度 8px 圆角，不用厚边框或大面积渐变。左侧是一列小图标＋层级标签；主列是对齐的模块带，每带 2–4 个紧凑单元，模块有小线性图标、粗体短标题和一行次级说明。连线短、正交、箭头明确，避免穿文字，箭头只表达确认过的关系。可选能力用虚线与「可选」标签。必要时右侧留出约 22% 宽的解释栏，使用灯泡／检查项／边界说明，不在侧栏堆长段落。

图标用统一的工程线性图标：用户、网页、钥匙、计划、代码文件、试管、放大镜、数据库、队列、容器、分支、盾牌。仅通用图标，不编造技术品牌标志。强调色按意义固定：蓝=主流程，青=机器测试，橙=人工审批或条件，紫=可选队列；不要彩虹配色。

底部：一条深蓝总结带，白字写一句经过核对的核心结论；其下最多两行小字说明口径。内容超多时缩短标签并用正文承接，不把所有源码路径和 API 都挤在图中。数字卡片采用较小的数字与紧凑分组，有清晰统计层次，不用四个巨大数字占满一页。

硬约束：美观不能改变事实；不新增源码没有的组件；不把可选项变默认；不把运行示例当实测；不把文件级裁判写成官方成绩；不画未实现的自动接管、高可用、向量数据库或恰好一次副作用。中文、参数、箭头方向在输出后逐项复核。

## 图 1：总体架构

标题：「从开发需求，到可验证的补丁」；副标题：「四角色串行协作 · 受控工具 · 持久化证据」。采用竖版，左侧六个层级：用户入口、API 服务、Agent 编排、工具边界、状态与索引、交付。

1. 用户入口：开发者 → Vue 3 工作台；卡片内「本地需求／GitHub Issue」「计划审批」「事件／Diff」。
2. API 服务：FastAPI，卡片内 API Key、目录授权、SSE。请求从工作台向 API，SSE 从 API 返回工作台，可用外侧细线呈现。
3. Agent 编排：深蓝框围住 Planner → Coder → Tester → Reviewer，并标「串行／返工共享 2 轮」。旁边单独的模型卡片「OpenAI 兼容 API」与 Runtime 连线。Planner 只读出计划，人工批准后才进入 Coder。
4. 工具边界：工具注册与角色权限 → 三列 Repository MCP（只读＋Hybrid RAG）、本地写入（只改已有文件）、Docker Sandbox（真实测试／命令）。写入工具与只读 Sandbox 分开。
5. 状态与索引：业务库「SQLite 默认／MySQL 可选」，执行服务写任务、事件、工具记录、检查点；独立小卡「目标仓库/.devpilot 本地索引」，仅连接 Repository MCP；目标仓库接受本地写入并只读挂载给 Sandbox。索引不是业务库。
6. 交付：Diff／测试／审查 → 二次人工确认 → GitHub MCP 创建 Draft PR。GitHub MCP 也在需求导入路径读 Issue，主图可用标注而非交叉长线。

右侧解释栏：①「默认：SQLite + inline，API 后台线程执行」。②「可选：API 入队 → SQL／Redis → Worker → 执行服务」，虚线箭头；Redis 只存队列，历史仍写业务库。③「测试通过 + Reviewer 批准才完成；独立研究裁判另外复验」。

底部总结带：「角色有分工，工具有边界，结论有证据」。脚注：「可选部署需显式配置；源码截至 2026-10-06」。所有节点与箭头不得添加 Kafka、LangGraph、JWT、向量数据库、K8s Job 或 microVM。

## 图 2：任务状态机

标题「任务状态与迁移条件」。主列采用三列表格「来源状态／目标状态／触发条件」，右栏列出七个状态小卡，不绘制跨卡片连线。完整九行迁移为：awaiting_approval→running（inline 批准／Worker 领取）；awaiting_approval→cancelled（仅队列模式取消未领取）；running→completed（测试通过且审查批准）；running→failed（执行／协议／验证失败）；running→cancelling（请求取消）；cancelling→cancelled（协作式取消点）；running 或 cancelling→interrupted（inline 重启／队列失租）；interrupted→running（用户显式恢复后领取）；failed→running（仅队列模式剩余尝试重试）。右栏状态为 awaiting_approval、running、completed、failed、cancelling、cancelled、interrupted；中文「已取消」必须完整。表格下解释 queued／claimed／done／dead 属于队列状态、approved 为预留值。总结带「重连是继续观察；恢复是重新执行」。

## 图 3：本地任务时序

标题「一次任务的完整执行链」。横版，6 个小图标泳道：用户、Vue、API、状态库、Agent Runtime、Sandbox。将主图分三段浅色背景「计划」「批准与执行」「验证与观察」，使用编号短消息、细生命线。规划时 API 调用 Planner；批准后 API 执行容量检查和 CAS，再启动独立后台线程。消息 10 用横跨 API 到 Agent 区域的浅橙注释框「API 启动独立后台线程」表示，不画数据库发起线程的箭头。其他消息以 final-prompts.json 的完整事实约束为准。SSE 必须是 API→Vue，数据先持久化再由 API 查询。右下注框「图为默认 inline；队列模式由 Worker 领取」。总结带「后台执行独立于浏览器连接」。

## 图 4：纵深防御

标题「把执行风险，约束在工具边界内」。竖版五层，每层有盾牌／钥匙／工具／文件／容器图标、一个短标题和两项核对规则：API Key＋仓库授权；角色可见工具；execute_tool 二次校验；resolve＋relative_to、仅已有文件、敏感路径保护；Docker 禁网、只读、512 MiB、1 CPU、128 PID、tmpfs 64 MiB。第4层侧支写工具→目标仓库，第5层只处理测试与命令。右栏「隐藏 Schema 不够」「解释器仍可执行任意容器代码」「Docker socket 仅可信演示」。总结带「权限校验与容器隔离共同约束执行」。

## 图 5：三层评测

标题「分三层，验证三种不同能力」。采用精细三层阶梯／金字塔，图形约占主列一半，右侧对应三层的指标解释，不能错配。底层合成回归：「12 fixture + verifier」「12/12 初始基线失败」，对应问题「验收能否识别初始缺陷？」；中层组件检索：「720 参数／32 查询」「16 开发＋16 验证」「Recall@5、MRR@5」，对应「能否找到相关文件？」；顶层真实缺陷：「SWE-bench Verified 来源」「双校准」「9题×2次」，对应「补丁能否通过独立测试？」。每层一枚小图标，数字只作短标签。注「初始失败不等于12/12修复」「文件级裁判，非官方resolved」。总结带「检索相关、流程完成、补丁正确，要分别验证」。

## 图 6：真实结果

标题「真实缺陷评测：把结果和口径放在一起」。横版，以三列细框统计栏展现独立测试14/18（77.8%）、工作流合规11/18（61.1%）、两者交集10/18（55.6%）；数字字号适中，下面用精确18格小矩阵分别标通过与其余，不用扭曲比例的装饰图。上方小眉题「冻结批次 2026-10-05 · 9题×2次」。下方一行紧凑统计「两次均修对6/9」「至少一次8/9」「3,236,730 Token」「平均211.8秒」。解释栏写模型deepseek-v4-flash、temperature0.2、缓存修复补跑、最初10实例中1无效。总结带「完整成功 = 独立测试通过 ∩ 工作流合规」。脚注「本项目文件级裁判，非官方 SWE-bench resolved；保留18次全部结果」。

## 图 7：Hybrid RAG

标题「先建源码索引，再融合两路检索」。横版，上下两带：上带源码→分块→CodeChunk，分别生成归一化源码向量矩阵与BM25源码分词语料；下带query分为query向量化→向量Top20、query分词→BM25 Top20，分别引用上带相应索引。两路结果→加权RRF→每文件最高分chunk→TopK。查询不能生成源码语料。公式卡采用score=2w/(k+rank_vector)+2(1-w)/(k+rank_bm25)，缺一路贡献0；默认w0.5、k60、rank从1。右侧说明产品K8／评测K5、384维MiniLM、.devpilot三文件与指纹重建。总结带「语义召回与关键词匹配，按排名融合」。

## 图 8：上下文压缩

标题「保留目标和近期因果链，压缩旧观测」。横版对比，使用消息带、文件小图标和配对连接线，左列是system、原始任务、旧回合和重复观测、最近完整回合；右列依次system、原始任务、≤6,000字符程序压缩记录、最近12条消息（边界回退可超过12）。旧回合以3–4条示意块呈现，不画虚构具体任务。中间细箭头标程序抽取／去重，不调LLM摘要。右侧小注：已修改文件／最后测试保留；单observation≤10,000字符保留首尾；read_file用SHA-256。总结带「字符限制是上下文控制，不是费用节省实测」。

## 图 9：背压与 fencing

标题「限制积压，识别失租执行者」。竖版上下两大区，上区三处容量闸门分别标inline每API8、queued深度100、每Worker并发2，两条执行路径分开；满时429＋Retry-After，Worker满时停止领取。下区令牌时间线：claim增加token→合法持有→30秒心跳／300秒租约→写入前校验；失租支路→停止后续写入与协作取消→队列dead／业务interrupted→确认停止后显式恢复。右栏准确说明MySQL深度软上限、检查与跨库写非同一事务、不能抢占工具或回滚文件。总结带「领取令牌约束后续写入，不保证副作用恰好一次」。

## 图 10：存储与队列矩阵

标题「业务历史与任务调度，独立选择」。横版精细表格，2行×3列，每格小数据库图标＋短句，严格使用figures.json图10六格文本。只突出sqlite+inline默认格，蓝色小角标「默认」。顶栏解释DATABASE_BACKEND选择历史库，TASK_QUEUE_BACKEND选择执行方式。下栏三项解释：sqlite队列名实际SQL实现跟随状态库；Redis仅存队列；改配置重建容器、历史显式迁移。总结带「启用Redis队列，不会把业务历史搬到Redis」。

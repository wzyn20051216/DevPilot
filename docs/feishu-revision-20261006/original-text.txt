[1352 heading2] 一、🎾 项目简介与简历写法
[1351 heading3] 1.1 项目是什么
[1350 text] DevPilot 是一个面向真实代码仓库的 AI 软件工程平台。用户可以输入本地开发任务，也可以导入 GitHub Issue；系统先分析仓库并生成计划，等待人工审批后，再由 Agent 调用代码检索、文件修改、测试执行和 Git Diff 等工具完成任务。
[1349 text] 它解决的核心问题不是「让大模型聊天」，而是把不稳定的模型输出约束在一条可观察、可验证、可中断的工程流程中。具体体现为六条分工：
[1348 ordered] LLM 只负责推理和选择工具，不直接接触宿主机 Shell。
[1347 ordered] 工具层负责执行动作，并在执行时实施路径、权限和命令边界。
[1346 ordered] 独立测试负责裁决结果，Agent 的文字声明不算成功。
[1345 ordered] 持久化 Trace 负责保存过程（任务、事件、工具调用），浏览器断线不会终止后台任务。
[1344 ordered] 人工审批负责高风险边界，代码执行与 GitHub 发布分别确认。
[1343 ordered] 评测系统负责验证价值，同时保留成功案例与失败案例。
[1342 text] 💡 为什么这样设计？ 大模型输出是概率性的：同样输入可能给出不同答案，甚至「自信地做错」。工程化的关键，是在模型外围加一圈确定性的脚手架——固定的工具、固定的状态机、固定的验收标准。模型可以变，脚手架不变。

[1316 heading3] 1.4 面试时如何用一分钟介绍
[1313 text] DevPilot 是我做的代码 Agent 工程化项目。它不是简单调用一次大模型，而是让模型通过受控工具读取和修改真实仓库。任务先生成计划并由用户审批，执行进入后台线程，所有事件和工具调用写入状态库，因此前端断线后可以继续接收。
[1314 text] 测试在只读、禁网、限资源的 Docker 容器中运行，最终是否成功由独立 verifier 决定——模型自己说「过了」不算。我还实现了 Hybrid Code RAG，并用四种 Agent/RAG 组合做对照评测；在 9 道真实 SWE-bench Issue 的 18 次重复中，文件级独立测试通过 14/18。
[1315 text] 工程侧最花功夫的是可靠性：把任务队列做成 SQL 与 Redis 双后端，Redis 用 Lua 保证原子领取，加了 fencing 令牌防止失租执行者乱写，还有入队/并发/背压三层限流。这些不是炫技，而是「多机跑一个任务队列」时真正会踩的坑。

[1302 heading2] 二、🥝 前置知识
[1301 text] 这一章是为了让没接触过 Agent 开发的人也能读懂后面。如果你已经熟悉，可以跳到第三章。
[1299 heading3] 2.1 LLM、Tool Calling 与 Agent
[1298 text] LLM 本身只生成文本或结构化参数。它不能读文件、不能跑测试、不能改代码。所谓 Agent，就是在模型外部增加一个循环：
[1297 code] 用户任务
  → [ 组装上下文 ] → 调用 LLM
  → LLM 返回：要么给最终答案，要么请求调用工具
  → 如果需要工具：执行工具，把结果塞回上下文，回到第一步
  → 循环直到给出最终答案 / 达到上限
[1296 text] 这个循环里，模型是「大脑」，工具是「手脚」，循环控制逻辑是「脊髓反射」——它决定了什么时候停、什么时候重试、出错怎么办。
[1295 text] 💡 关键洞察：Agent 的可靠性，更多取决于循环控制逻辑，而不是模型本身。同一个模型，配上不同的工具边界、重试策略和验收逻辑，效果可能天差地别。
[1293 text] DevPilot 的 BaseToolAgent.run_stream() 就是这个循环。每轮都会记录 thinking、tool_call 和 tool_result 事件；达到最大轮数、超过 Token 预算或发生异常时，必须输出明确的 error，不能假装完成。
[1292 heading3] 2.2 State 与 Event 的区别
[1291 text] 这是初学者最容易混淆的一对概念：
[1290 bullet] State（状态）：某一时刻的完整快照。例如：当前轮次、已修改文件列表、测试报告、累计 Token。
[1289 bullet] Event（事件）：刚刚发生的一个动作。例如：开始、工具调用、角色交接、测试结果、错误。
[1288 text] 打个比方：State 是「此刻房间的照片」，Event 是「监控录像的一帧」。
[1287 text] 为什么要有这个区分？
[1286 bullet] 传 State 给前端，每帧都要传全量，浪费带宽，也无法表达「变化过程」。
[1285 bullet] 传 Event 更适合 SSE，也更容易持久化和回放——把事件按顺序存下来，就能重放整个执行过程。
[1284 text] DevPilot 在 Agent 内部用 AgentState 聚合状态，对外用 AgentEvent 传输增量事件。
[1283 heading3] 2.3 SSE 流式会话
[1282 text] SSE（Server-Sent Events）是基于 HTTP 的服务端单向事件流：浏览器用 text/event-stream 持续接收消息。它比 WebSocket 更适合「客户端提交任务，服务端持续推送进度」的场景——因为不需要双向通信，实现更简单。
[1281 text] 早期最常见的错误，是把 Agent 生成器直接绑定在 SSE 请求上：
[1280 code] ❌ 错误做法：HTTP 请求 → 运行 Agent → 边跑边推送
问题：浏览器一断线，生成器被销毁，任务也停了。
[1279 text] DevPilot 的做法是把连接的生命周期和任务的生命周期解耦：
[1278 ordered] /execute 原子地把任务从 awaiting_approval 改成 running。
[1277 ordered] 后台线程独立运行 Agent。
[1276 ordered] 每条事件先写入状态库，并分配递增 sequence。
[1275 ordered] SSE 只轮询并转发数据库中的新增事件。
[1274 ordered] 客户端用 after_sequence 从断点继续。
[1273 text] 因此，连接断了，任务照跑。
[1272 heading3] 2.4 多 Agent 与工作流
[1271 text] 多 Agent 并不天然优于单 Agent。 很多人以为「角色越多越智能」，其实角色拆分带来的价值是隔离职责和权限：
[1270 bullet] Tester 不能写文件，只能跑测试并如实报告结果。
[1269 bullet] Reviewer 独立阅读 Diff，不参与写代码，因此不会为自己的代码辩护。
[1268 bullet] Planner 只做计划，不碰代码。
[1267 text] 代价则是：结构化输出失败点变多、上下文重复、延迟增加。
[1266 text] DevPilot 因此同时保留单 Agent 与多 Agent 模式，并用实验决定默认值，而不是假设「多 Agent 一定更好」。
[1264 heading3] 2.5 Human-in-the-loop（人在回路）
[1263 text] 高风险动作不能只靠 Prompt 约束——因为 Prompt 可能被绕过，也可能被模型「善意地误解」。DevPilot 设置两个明确的审批点：
[1262 ordered] 执行审批：Planner 只生成计划，用户批准后 Coder 才能修改文件。
[1261 ordered] 发布审批：系统先生成 PR Preview 和代码快照，用户确认后才创建分支、提交并发布 Draft PR。
[1260 text] 第二个审批点还会重新计算 snapshot_hash。如果审批后文件发生变化，发布会被阻止——避免「用户批准的内容」与「实际推送的内容」不一致。
[1259 text] 💡 这个机制对应安全领域的 TOCTOU 防护（Time-of-Check to Time-of-Use）：检查时的内容，必须与使用时的内容一致。
[1257 heading3] 2.6 MCP（Model Context Protocol）
[1256 text] MCP 把「模型可调用的工具」抽象为可发现的协议服务。简单说：它是一套标准，让模型能动态「发现」有哪些工具可用，而不用把工具硬编码进提示词。
[1255 text] DevPilot 把仓库只读能力放在 Repository MCP Server 中：
[1254 bullet] list_files、read_file、search_code、retrieve_code、git_diff
[1253 text] 客户端在一次 Agent 运行开始时做 tool discovery，再按角色白名单过滤。
[1252 text] 为什么写文件和执行命令不放进 MCP？ 因为它们需要更严格的路径、权限和沙箱边界——只读能力可以协议化，写操作必须走本地受控工具。
[1251 heading3] 2.7 Hybrid Code RAG（混合代码检索）
[1250 text] 🖼️ 配图位 · 图 7：混合检索 RRF 流程图（绘图提示词见《配图提示词》图 7；生成后替换本行）
[1248 text] 普通 RAG 面向自然语言文档，Code RAG 还要保留文件、符号和行号信息。DevPilot 的索引流程是：
[1247 code] 源码文件
  → 按 AST 或滑动窗口分块
  → 生成带文件名和符号名的 embedding_text
  → all-MiniLM-L6-v2 生成 384 维归一化向量
  → 同时建立 BM25 语料
[1246 text] 查询阶段分别取向量检索 Top 20 和 BM25 Top 20，再用 RRF（Reciprocal Rank Fusion） 融合：
[1245 code] RRF(d) = Σ  1 / (60 + rank_i(d))
[1244 text] 最后按文件去重，每个文件只保留最高分 chunk——避免同一个测试文件的多个片段挤占全部结果。
[1243 text] 为什么要混合检索？
[1242 bullet] 向量检索：语义相近但词面不同的查询（如「处理超时」→「timeout handling」）
[1241 bullet] BM25：函数名、配置项、异常名等精确词匹配
[1240 bullet] RRF 融合：只依赖排名而非原始分数，避免两套分数尺度不一致
[1239 heading3] 2.8 为什么检索指标高，修复率仍可能下降
[1238 text] 这是本项目最反直觉、也最值得讲的发现：
[1237 text] 检索系统回答的是「相关文件能否被找到」； Agent 任务回答的是「模型能否基于证据完成正确修改」。 两者之间还隔着理解、工具选择、运行时验证和兼容性推断。
[1235 text] DevPilot 的文件级检索指标很好，但在小样本真实修复中，RAG 的修复率并未高于无 RAG。原因包括：
[1234 bullet] 额外上下文会形成错误锚点，把模型引到不相关的方向。
[1233 bullet] 检索结果可能相关，却不是决定行为的运行时证据。
[1232 bullet] 小仓库本来就能通过 list_files + search_code + read_file 快速定位。
[1231 bullet] RAG 增加索引和推理延迟。
[1230 text] 结论：RAG 应当是可评测、可关闭、可按仓库规模启用的能力——而不是「有就一定开」。
[1229 heading3] 2.9 上下文压缩
[1228 text] 🖼️ 配图位 · 图 8：上下文压缩前后对比图（绘图提示词见《配图提示词》图 8；生成后替换本行）
[1226 text] Tool Calling 长任务会重复携带历史消息，输入 Token 往往呈近似二次增长——对话越长，每一轮都在重发全部历史。DevPilot 的确定性压缩策略是：
[1225 bullet] 永久保留 system message 和用户原始 Issue。
[1224 bullet] 完整保留最近 12 条消息。
[1223 bullet] 把更早的工具回合压缩为最多 6,000 字符的结构化记录。
[1222 bullet] 保留已修改文件和最近测试结论。
[1221 bullet] 裁剪点回退到 assistant tool call 边界，避免出现「孤立的 tool result」（有结果没调用，模型会困惑）。
[1220 bullet] 单次工具 observation 最多进入上下文 10,000 字符。
[1219 text] 这类压缩不会让模型「记住一切」，但能保证任务目标、近期因果链、关键事实仍然存在。
[1217 heading3] 2.10 独立 Verifier（独立裁决器）
[1216 text] Agent 说「测试通过」不等于代码正确。 DevPilot 把验证分成两层：
[1215 bullet] 运行流程中的 Tester：为 Agent 提供反馈，帮助它在任务过程中自我修正。
[1214 bullet] 评测器（独立 Verifier）：在 Agent 结束后，从受保护的验证目标重新运行测试——它不看 Agent 说了什么，只看真实结果。
[1213 text] 真实缺陷评测还会排除候选补丁对测试文件和测试配置的修改，防止 Agent 通过删除断言来「修复」任务。
[1212 text] 💡 一句话：能改测试的 Agent，一定会改测试。
[1209 heading2] 三、⚾️ 业务背景
[1208 heading3] 3.1 使用场景
[1207 text] 开发者面对一个不熟悉的仓库和 Issue 时，需要完成定位、修改、测试、审查和发布。普通聊天模型只能给建议；全自动 Agent 又可能误改文件、执行危险命令或错误宣称成功。
[1206 text] DevPilot 的目标用户是希望观察和控制执行过程的开发者。典型任务包括：
[1205 bullet] 修复明确的后端 Bug。
[1204 bullet] 修改配置传播逻辑。
[1203 bullet] 实现一个范围受控的小功能。
[1202 bullet] 从 GitHub Issue 生成计划并形成 Draft PR。
[1201 bullet] 对比单 Agent、多 Agent、RAG 和无 RAG 的效果。
[1200 heading3] 3.2 核心需求
[1199 text] 把「模型随机性」与「工程确定性」隔离开，需要满足四条：
[1198 ordered] 可控：高风险动作（改文件、发布）必须人工审批。
[1197 ordered] 可观察：每一步都能看到模型在想什么、调了什么工具、得到什么结果。
[1196 ordered] 可验证：成功与否由独立测试裁决，而非模型自述。
[1195 ordered] 可恢复：断线、重启、取消都不能让任务「半死不活」。
[1194 heading3] 3.3 设计原则
[1193 bullet] 默认保守：默认策略由实验数据决定，不选「看起来更炫」的方案
[1192 bullet] 纵深防御：权限、路径、命令、沙箱多层校验，任何一层都不单独承担安全
[1191 bullet] 确定性优先：能用代码保证的，不交给 Prompt
[1190 bullet] 证据优先：结论必须附带代码、命令、原始报告和失败案例
[1189 bullet] 诚实边界：明确写出「未做」「未验证」的部分，不夸大
[1187 heading2] 四、🐧 项目流程
[1186 heading3] 4.1 本地任务主流程（一张图看懂）

[1182 text] 关键点逐条解释：

[1177 heading3] 4.2 多 Agent 流程
[1176 code] Planner 输出计划
  ↓
Coder 修改代码并查看 Git Diff
  ↓
Tester 运行真实测试
  ├─ 失败：把 stdout/stderr 交还 Coder，最多返工 2 轮
  └─ 通过：进入 Reviewer
  ↓
Reviewer 独立检查需求、边界和非必要修改
  ├─ approved = true：完成
  └─ approved = false：交还 Coder 返工（与测试失败共享同一返工预算）
[1175 text] 返工规则（max_repair_rounds 默认 2）：
[1174 bullet] 测试失败与审查拒绝共享同一返工预算，因此不会「测试返工 2 次 + 审查返工 2 次」无限循环。
[1173 bullet] 每次返工都携带完整原始需求、计划、上游失败报告，从入口重新执行，不沿用旧结论。
[1172 bullet] 每次 Coder 执行后重新验证，不复用旧的测试通过或审查批准。
[1171 text] 结构化输出与失败分类：Planner、Tester、Reviewer 的最终输出都要经过 Pydantic Schema 校验。系统会尝试提取 JSON、做有限的格式修复；最终仍无法通过 Schema 时，发出 protocol_error，禁止向下游交接——因为「格式坏了」和「结论错了」必须区分对待。
[1170 heading3] 4.3 GitHub Issue 流程
[1169 ordered] 用户填写 owner、repo、Issue 编号和本地仓库路径。
[1168 ordered] GitHub MCP 读取 Issue 标题、正文和元数据。
[1167 ordered] 系统把 Issue 转换为完整开发请求。
[1166 ordered] Planner 生成计划并保存任务来源。
[1165 ordered] 后续执行流程与本地任务一致。
[1164 ordered] 完成后生成只读 PR Preview。
[1163 ordered] 用户二次审批后创建分支、提交文件并发布 Draft PR。
[1162 heading3] 4.4 取消、断线与恢复
[1161 bullet] 取消：状态先变 cancelling，后台设置 threading.Event；Agent 在每轮模型调用和工具调用边界检查，随后写入 cancelled
[1160 bullet] 断线续传：前端记录最后事件序号，重连 /events?after_sequence=N
[1159 bullet] 进程重启：仅 inline 模式启动时把遗留 running/cancelling 标记为 interrupted；队列模式 API 重启不影响独立 Worker 的任务
[1158 bullet] 租约过期：SQL 队列租约到期的任务被隔离为 dead，确认旧 Worker 停止后才允许显式恢复
[1157 bullet] 恢复：用户显式调用 /resume，系统从已批准的计划重新执行
[1156 text] ⚠️ 诚实的边界：execute_stream 仍从编排入口运行，阶段、返工计数与工具副作用没有事务恢复。检查点会校验调用配对、保留系统和原始任务，但不能描述为「无损续跑」——已经发生的文件写入无法回滚。

[1148 text] 与初版的区别（这几块是新增的）：
[1147 bullet] API Key 鉴权层：所有业务请求先过 require_api_key。
[1146 bullet] 任务队列：inline 时是进程内线程，sqlite/redis 时是持久化队列 + 独立 Worker。
[1145 bullet] fencing 校验：执行服务写事件/状态前校验「本执行者是否仍是任务的合法持有者」。
[1144 bullet] 双后端状态库：SQLite 或 MySQL，由统一方言适配层屏蔽差异。
[1143 heading3] 5.2 分层职责
[1142 bullet] API 层（main.py、schemas.py）：鉴权、参数校验、路由、SSE 转发（不做什么：不直接操作仓库）
[1141 bullet] 服务层（services/）：任务执行、队列、发布、上下文（不做什么：不包含模型提示词逻辑）
[1140 bullet] Agent 层（agents/）：Tool Calling 循环、角色、编排（不做什么：不绕过工具直接动文件）
[1139 bullet] 工具层（tools/、mcp_*）：实际执行动作，实施边界（不做什么：不做业务决策）
[1138 bullet] 数据层（database/）：状态库读写、方言适配（不做什么：不包含业务规则）
[1137 text] 💡 分层的意义：每层只依赖下一层的接口。比如 Agent 层不知道底层是 SQLite 还是 MySQL——换数据库时，Agent 代码一行不改。

[1130 heading3] 5.4 数据模型
[1129 text] 状态库共 9 张表，职责如下：
[1128 bullet] tasks：任务主体：仓库路径、需求、状态、执行模式
[1127 bullet] plan_steps：审批通过的执行计划步骤
[1126 bullet] agent_events：全量事件流（含递增 sequence），SSE 的数据源
[1125 bullet] tool_calls：工具调用的参数、结果预览、耗时、成败
[1124 bullet] task_sources：任务来源（本地 / GitHub Issue）
[1123 bullet] publish_previews：PR 预览、快照 Hash、发布状态
[1122 bullet] evaluation_results：评测结果记录
[1121 bullet] task_queue：队列任务（含 fence_token、租约、尝试次数）
[1120 bullet] agent_contexts：上下文检查点，用于中断恢复
[1119 text] 💡 一个细节：数据库启用外键和 WAL（Write-Ahead Logging）。WAL 可以提升单机读写并发，但不能代替多实例任务队列——这是两个层面的问题。
[1116 heading2] 六、🧩 核心实现拆解
[1115 heading3] 6.1 BaseToolAgent：统一的工具循环
[1114 text] backend/src/agents/base_tool_agent.py 处理所有角色共有的机制：
[1113 ordered] 初始化 State 并发送 start。
[1112 ordered] 发现 MCP 工具并按白名单过滤。
[1111 ordered] 压缩旧上下文（见 2.9）。
[1110 ordered] 调用 OpenAI 兼容的 Chat Completions。
[1109 ordered] 累加 Token 和 LLM 耗时。
[1108 ordered] 解析 Tool Call 参数并发送 tool_call。
[1107 ordered] 在注册表执行工具，把异常也转换为 observation（而不是直接崩溃）。
[1106 ordered] 截断过长的工具结果并发送 tool_result。
[1105 ordered] 无工具调用时输出 final。
[1104 ordered] 最大轮数后进行一次禁止工具的强制收尾；仍不合法则失败。
[1103 text] 💡 为什么把循环集中在基类？ 让角色只定义 Prompt、工具权限和迭代上限，循环逻辑只有一份。改一次，四个角色都受益——这就是「消灭重复」。
[1101 heading3] 6.2 两层工具权限（纵深防御）
[1100 text] 🖼️ 配图位 · 图 4：纵深防御分层图（绘图提示词见《配图提示词》图 4；生成后替换本行）
[1098 bullet] 第一层在 get_tool_definitions()：模型只能看见当前角色允许的工具。
[1097 bullet] 第二层在 execute_tool()：即使手工构造了未授权的 Tool Call，执行时仍会抛出 PermissionError。
[1096 text] 💡 这叫 defense in depth（纵深防御）。只隐藏工具 Schema 是不够的——模型可能通过提示词注入、或者干脆「编造」一个未授权的工具名。真正的安全边界必须在执行层。
[1094 heading3] 6.3 文件安全
[1093 text] 所有文件路径都遵循三步校验：
[1092 code] 1. 与仓库根目录拼接
2. 执行 resolve()（解析符号链接）
3. 通过 relative_to(base_path) 确认目标仍在仓库内
[1091 text] 因此 ../../secret 和指向仓库外的符号链接都会被拒绝。
[1090 text] 其他限制：
[1089 bullet] 磁盘文件默认不能超过 1 MB。
[1088 bullet] 进入上下文的内容按字符数截断。
[1087 bullet] Coder 修改大文件时优先使用唯一原文锚点的 replace_in_file，减少整文件重写带来的误删风险。
[1086 heading3] 6.4 Docker Sandbox（隔离执行）
[1085 text] 允许的程序包括 python、pytest、ruff、mypy，以及 node、npx、javac、java；以 sandbox/docker_runner.py 白名单为准。命令使用 argv 数组 + shell=False——从根本上杜绝 shell 注入。
[1084 text] 容器限制：
[1083 code] --network none                                   # 完全禁网
--memory 512m                                    # 内存上限
--cpus 1.0                                        # CPU 上限
--pids-limit 128                                  # 进程数上限
--read-only                                       # 根文件系统只读
--tmpfs /tmp:rw,noexec,nosuid,size=64m            # 临时目录不可执行
--mount source=<repo>,target=/workspace,readonly  # 仓库只读挂载
[1082 text] 这意味着：测试命令可以读取候选代码，但不能借测试过程修改宿主机仓库，也不能访问外网。
[1081 heading3] 6.5 结构化输出（让模型「说人话」变成「说机器话」）
[1080 text] Planner、Tester、Reviewer 分别映射到 PlannerProtocolOutput、TesterProtocolOutput、ReviewerProtocolOutput。结构化输出层会：
[1079 bullet] 从 Markdown 代码块或混合文本中提取 JSON。
[1078 bullet] 对常见控制字符问题做有限修复。
[1077 bullet] 最终用 Pydantic 严格校验字段和类型。
[1076 bullet] 拒绝未知字段和隐式类型转换（如字符串 "true" 冒充布尔 true）。
[1075 text] 协议还内建了语义一致性校验（这是最巧妙的部分）：
[1074 bullet] Coder：status = blocked 时必须在 risks 中说明阻塞原因，不能空报告跳过
[1073 bullet] Reviewer：approved = true 时 issues 必须为空；拒绝时必须列出具体问题
[1072 bullet] Planner：计划步骤 id 必须唯一且为正整数
[1071 text] 💡 宽容解析只处理「表达形式」，不绕过「语义 Schema」。 换句话说：你可以少写个引号，但不能把「测试失败」说成「测试通过」。
[1069 heading3] 6.6 后台执行与 Trace
[1068 text] 🖼️ 配图位 · 图 9：背压与 Fencing 示意图（绘图提示词见《配图提示词》图 9；生成后替换本行）
[1066 text] TaskExecutionService 为每个运行任务维护后台线程和取消事件。执行产生的事件会先保存，再由 SSE 查询。Tool Result 同时提取为独立 tool_calls 记录，因此可以计算：
[1065 bullet] 总事件数和 Tool Call 数。
[1064 bullet] 失败工具数。
[1063 bullet] 总 Token 与估算成本。
[1062 bullet] LLM 耗时和工具耗时。
[1061 bullet] 每个 Agent 的调用分布。
[1060 bullet] RAG 调用次数和检索耗时。
[1059 text] fencing 保护：执行服务在持久化每个事件前、写检查点前、写最终状态前都校验租约。一旦失去租约（例如被另一个 Worker 接管），立刻停止写入并触发取消。
[1058 text] ⚠️ 诚实边界：已经发出的工具调用（正在跑的测试、正在落盘的写文件）无法被抢占。保证的是「旧执行者不能再写事件/状态」，不是「副作用恰好一次」。
[1056 heading3] 6.7 发布一致性（TOCTOU 防护）
[1055 text] 发布前收集变更文件并计算快照 Hash。Preview 保存目标分支、Head 分支、Commit Message、PR 标题和正文。真正发布时再次计算 Hash；任何变更都会使旧审批失效。
[1054 text] 💡 这对应安全系统中的 TOCTOU 防护：检查时的内容必须与使用时的内容一致。用户批准的是「这一份代码」，不是「这个分支名」。
[1051 heading2] 七、🧪 评测设计与真实结果
[1050 text] 这一章回答一个问题：你怎么知道这东西真的有用？ 答案是：不靠感觉，靠可复现的分层评测。
[1048 heading3] 7.1 为什么需要三层评测
[1047 text] 🖼️ 配图位 · 图 5：三层评测金字塔（绘图提示词见《配图提示词》图 5；生成后替换本行）
[1045 text] 只做组件评测，会把「找得到文件」误当成「修得好代码」；只展示 Demo，又无法知道失败率。因此 DevPilot 用三层：
[1044 bullet] 合成回归：我的改动有没有破坏已知能力？（手段：12 个自建 fixture + 独立 verifier）
[1043 bullet] 组件评测：RAG 检索准不准？（手段：标注查询 + Recall@K / MRR）
[1042 bullet] 真实缺陷：能不能修真实仓库的 Bug？（手段：SWE-bench Verified + 双校准门禁）
[1041 heading3] 7.2 四种架构变量（对照实验的基石）
[1040 bullet] single_no_rag：单 Agent，不用检索
[1039 bullet] single_rag：单 Agent，用混合检索
[1038 bullet] multi_no_rag：多 Agent，不用检索
[1037 bullet] multi_rag：多 Agent，用混合检索（当前默认）
[1036 text] 每次运行都会记录：成功与否、测试结果、工具调用、迭代次数、返工次数、耗时、Token、LLM/工具耗时、工作区和错误信息——这样才能做同题配对对比，而不是「跑一次感觉不错」。
[1035 text] 💡 注意：前端只暴露 multi_rag 与 multi_no_rag 两个选项（默认 multi_rag）。single_* 变体是研究用的实验开关，不面向最终用户。
[1033 heading3] 7.3 合成回归（测「有没有退化」）
[1032 text] 当前数据集含 12 个 fixture：9 个 Python 基础任务（easy／medium／hard 各 3 个），另有 TypeScript、Java、Python 跨模块任务各 1 个。审计确认 12/12 初始 verifier 失败——即这些任务在未修复前确实是「坏的」，verifier 能识别。
[1031 text] 💡 为什么初始必须失败？ 如果一个任务在没修的时候测试就通过，那它根本证明不了 Anything。这叫「校准门禁」，是评测的第一道防线。
[1029 text] 它证明当前实现没有破坏已知能力，但不能代表真实仓库上的总体性能。
[1028 heading3] 7.4 RAG 检索评测
[1027 text] 参数网格：720 组配置、32 条人工查询；开发集选参、验证集报告（避免在验证集上过拟合）。
[1026 text] 最终结果：16 条验证查询的 Recall@5 为 84.38%、MRR 为 0.6615；返回内容的字符数相对同批默认减少 47.65%——用更少的上下文达到更好的检索精度。
[1025 text] 💡 首个索引构建包含 Embedding 模型冷启动，因此明显慢于后续样本。报告里要注明这一点，否则会误读性能。

[1006 heading3] 7.6 失败样本为什么有价值
[1005 text] 失败比成功更能说明问题。历史诊断中发现：
[1004 bullet] 模型会用不同作用域的对象替代 Issue 原始复现（改了「看起来像」的东西）。
[1003 bullet] 模型会误判生成器异常的边界（把环境错误当成代码错误）。
[1002 text] 这类失败直接指向「运行时探针」和「协议兼容检查」的能力缺口——比一个漂亮的成功案例更有信息量。
[1001 text] 💡 有的失败还暴露了评测环境本身的问题（工作区不完整造成假阴性）。修好环境后，同一个候选补丁能通过——所以评测基础设施本身也要被验证。
[999 heading3] 7.7 如何正确表达实验结论
[998 text] 可以说：
[997 bullet] 「在 12 个合成回归任务中，多 Agent 模式通过独立 verifier。」
[996 bullet] 「文件级 RAG 在 16 条验证查询上 Recall@5 为 84.38%。」
[995 bullet] 「9 道真实 Issue 各重复 2 次，文件级独立测试通过 14/18。」
[994 text] 不应说：
[993 bullet] ❌「DevPilot 修复真实 Bug 的成功率是 78%。」（样本太少，且是自研口径）
[992 bullet] ❌「RAG 已经显著提升代码修复效果。」（实验没有支持这个结论）
[991 bullet] ❌「多 Agent 一定比单 Agent 可靠。」（不同任务类型结论不同）
[990 text] 💡 为什么这么严格？ 因为样本量、重复次数和仓库类型都不足以支持泛化。一个诚实的 60% 比一个注水的 90% 更有价值——后者在面试中被追问一句「样本多大」就崩了。

[933 text] Q：Docker Sandbox 报路径不存在？ Compose 中应使用容器路径 /workspace/<project>，不能把 Windows 的 E:\... 直接传给 Backend。

[908 heading3] 10.1 当前边界（诚实清单）
[907 text] 评测边界
[906 bullet] 真实评测为 9 道有效 Issue、每题 2 次（18 次），是自研文件级口径，非官方榜单成绩；样本不足以泛化。
[905 bullet] 当前真实集主要是 Python，跨语言能力仅由合成 benchmark 部分覆盖。
[904 bullet] 失败样本诊断显示，模型在「运行时行为推断」和「协议兼容检查」上仍有缺口。
[903 text] 成本证据
[902 bullet] 上下文压缩（观测去重 + 摘要）在单次长任务上降低了 Token，但各一次不足以估计波动；cache 命中率是统计量，不是货币节省实测。
[901 text] 任务执行边界
[900 bullet] 队列已支持 SQL（SQLite / MySQL）+ Redis（Lua 原子） 双后端，含租约、心跳、fencing 令牌、有限重试与三处背压。
[899 bullet] 未做：Redis 仅单节点 / Sentinel，未做 Redis Cluster；无自动故障切换；MySQL 队列深度是软上限（并发入队可能小幅超出）。
[898 bullet] fencing 不能抢占在途工具调用：已发出的文件写入无法回滚。
[897 text] 恢复边界
[896 bullet] 状态库保存角色消息检查点，校验系统/原始请求保留、工具回合配对。但编排阶段和工具副作用未事务化，多角色流程仍从入口运行，不能承诺无损续跑或恰好一次执行。
[895 text] 部署边界
[894 bullet] API 已有 API Key 鉴权与仓库目录白名单；但未做 JWT / 多租户；共享 API Key 是应用级凭据，组织级用户身份管理未实现。
[893 bullet] K8s 文件是示例清单；每任务 Job 和 Firecracker 执行器尚未实现。
[892 bullet] 多机场景仅用「多进程同机」模拟，没有真实多主机 / 网络分区演练。
[891 heading3] 10.2 优先级最高的改进
[890 ordered] 扩样验收：逐项排查校准未过的实例；解决个别官方镜像启动错误；先用未调参任务做同题配对评测，再谈泛化。
[889 ordered] 探针配对实验：运行时协议探针已实现，下一步用有/无探针配对验证收益——采纳工具本身不等于正确修复。
[888 ordered] 动态 RAG 阈值：启发式决策已实现，但阈值尚未通过大仓库真实对照验收，不能声称自适应优于固定开关。

[884 heading2] 十一、💬 高频面试问题
[883 heading3] 11.1 为什么默认使用多 Agent + RAG？
[882 text] 因为它是当前证据支持的默认值，且面向用户的价值更完整：多 Agent 隔离了「写代码」与「做裁决」两种角色，混合检索在大型仓库中帮助定位。
[881 text] 注意：single_* 变体仍保留为实验开关，用于做消融对照。默认值由实验决定，而不是为了展示技术强行开启某个能力。
[879 heading3] 11.2 多 Agent 的价值是什么？
[878 text] 主要价值是职责、权限和验证视角的隔离：
[877 bullet] Tester 不可写文件，只能如实报告测试结果。
[876 bullet] Reviewer 独立读取 Diff，不为自己的代码辩护。
[875 text] 代价是更多模型调用、更多结构化输出边界和编排失败点。所以它需要和单 Agent 做消融实验，而不是默认假设更优。
[874 heading3] 11.3 为什么不用 LangGraph / 现成框架？
[873 text] 当前流程对事件结构、持久化、取消点、Token 统计和错误语义有明确要求。自研小型 Runtime 更容易展示底层机制并精确控制行为——尤其是 fencing、背压、租约这些框架不一定暴露的细节。
[872 text] 但：生产项目是否选框架，应依据团队维护成本、生态和工作流复杂度，而不是为了「自研」本身。面试时这样回答，既展示深度，又不显得偏执。
[871 heading3] 11.4 如何防止 Agent 执行危险命令？
[870 text] Prompt 只是第一层。真正的边界由以下共同实施：
[869 ordered] 角色工具白名单（模型看不见不该用的工具）。
[868 ordered] 执行层二次权限检查（手工构造的调用也会被拒）。
[867 ordered] 路径解析（resolve() + relative_to()）。
[866 ordered] 命令白名单 + shell=False（argv 数组，杜绝注入）。
[865 ordered] Docker Sandbox（禁网、只读、限资源）。
[864 heading3] 11.5 如何证明任务真的成功？
[863 text] 端到端成功要求：执行协议没有 error，并且独立 verifier 通过。真实评测还会先校准错误基线与金补丁，并保护测试文件，避免模型篡改验收标准。
[862 text] 一句话：能改测试的 Agent，一定会改测试。 所以验证必须在模型够不着的地方重跑。
[860 heading3] 11.6 SSE 断线为什么不影响任务？
[859 text] Agent 在后台线程中执行，事件写入状态库；SSE 只是数据库事件的消费者。重连时用事件序号继续读取——连接和任务拥有独立生命周期。
[858 heading3] 11.7 RAG 为什么使用 RRF？
[857 text] 向量相似度和 BM25 分数不在同一尺度，直接加权需要额外归一化和调参。RRF 只依赖排名，简单稳定，并能奖励同时被两路检索排在前面的结果。
[856 heading3] 11.8 如果做成生产系统，最先改什么？
[855 text] 先修可靠性基础设施，再优化模型策略：
[854 ordered] 真实多主机下的租约与 fencing 演练。
[853 ordered] 隔离 Docker daemon，实现每任务 microVM。
[852 ordered] 补齐配额与多租户权限。
[851 ordered] Redis 从单节点升级到集群 / Sentinel。
[850 text] 💡 为什么这个顺序？ 因为模型策略再优化，如果任务会丢、状态会错乱，一切白搭。基础设施的可靠性是 1，模型效果是后面的 0。
